Signing in without a key: identity federation, explained

The Claude Console offered to let your code call the API with no API key at all. This page explains what that offer really is, how the trust behind it works, and where it fits ELI5 Learner: not in the Mac app, but quite possibly in the nightly evals.

What the dialog said (Claude Console › Keys & access › API keys): "With identity federation, you don't need an API key. Your cloud or CI provider issues short-lived tokens that authenticate your requests — no static key to manage." Nothing to store in env vars, config files or secret managers; tokens rotate automatically and expire in minutes; works with GCP, AWS, Azure and GitHub Actions. "Local scripts, third-party tools, and environments without an identity provider may still need an API key."

In depth

The Password That Was Never There

Anthropic now lets machines prove who they are instead of carrying a secret. How the swap works, what it protects, and what it can't reach.

For most of the API era, calling Claude meant pasting a long string that begins sk-ant-api into an environment variable and hoping it stayed put. The dialog you saw in the Claude Console is Anthropic's invitation to stop doing that, at least for code that runs somewhere other than your own laptop.

The feature is called Workload Identity Federation, or WIF. Anthropic announced it as generally available on June 17, 2026, together with service accounts and an ant auth login command for interactive use. Its documentation describes it plainly: workloads "authenticate to the Claude API with short-lived OpenID Connect (OIDC) tokens instead of long-lived sk-ant-... API keys." The tokens come from an identity provider you already use, such as AWS, Google Cloud, Microsoft Entra ID, GitHub Actions, Kubernetes, SPIFFE or Okta.

Why it matters: an API key is a bearer secret. Anyone who holds it is you, as far as the API is concerned, for as long as it lives. Federation replaces it with a token that, in Anthropic's words, expires "in minutes rather than never," and it removes the stored secret entirely. It only works, though, where some trusted system can vouch for your code. A desktop app on your own Mac has no such system, so for ELI5 Learner the answer splits in two.

The trouble with a key that never expires

An API key works like a house key with no name on it. The API checks only that the string is valid; it does not ask who is presenting it or from where. That makes keys simple, and it makes leaks expensive. Keys end up in shell history, in CI logs, in a .env file committed by accident, in screenshots. Anthropic's own advice is to store keys in a secrets manager, rotate them periodically and delete any you suspect have leaked. The Console now lets you set an expiration when you create a key (3 hours, 1 day, 7 days, 30 days, a custom period, or Never), and organizations can cap it.

Anthropic has also changed what a key belongs to. A personal key acts as you and dies when you leave the organization. A service account key acts as a service account. The older workspace key belongs to no one and is now labeled legacy. Anthropic recommends a personal key for your own development and a service account for "shared or automated workloads (CI, production services)," so a bot does not break when the human who created its key departs.

Identity-backed keys fix ownership. They do not fix the underlying problem: there is still a durable secret that must be copied into the place where the code runs. Federation attacks that part.

A name for a machine

The sidebar entry "Service accounts" is the foundation. A service account, with an ID beginning svac_, is "a named, non-human identity inside your Anthropic organization." It has no email, no password and no Console login. It lives at the organization level and acts in a workspace only after you add it to that workspace (every service account is implicitly a member of the Default Workspace). Usage then counts against that workspace's rate limits and is attributed to it, the same as with a key.

Anthropic's documentation puts the distinction in one line: "A workspace API key is a credential, whereas a service account has credentials." A service account can hold a static service account key, or it can be the target of federation. Either way, the audit trail reads "the nightly-evals robot did this," not "some key did this."

Trust, written down once

Federation needs three objects in the Console, and the "Connect workload" wizard on the Workload identity page creates all three. Together they say, in Anthropic's phrasing, "tokens signed by issuer X, with claims that look like Y, may act as service account Z."

  • A federation issuer (fdis_…) registers an identity provider by its issuer URL, the exact value of the iss claim in its tokens. For GitHub Actions that is https://token.actions.githubusercontent.com. Anthropic finds the provider's public signing keys (its JWKS) through standard OIDC discovery, or you give a JWKS URL or paste the keys inline for private clusters.
  • A service account (svac_…), the identity the workload will act as.
  • A federation rule (fdrl_…) binds the two. It matches incoming tokens on a subject_prefix, an exact audience, exact values of other claims, or a Common Expression Language (CEL) condition. Every configured matcher must pass, and Anthropic refuses a rule that sets only an audience, so a rule cannot accidentally accept everything an issuer signs. The rule also sets the OAuth scope of the minted token and its lifetime: 60 seconds to 24 hours, with a 3,600-second API default; the wizard prefills 600.

Two details are easy to miss. The client names the rule it wants in every exchange; "there is no implicit rule search." And the rule's scope is a ceiling. workspace:developer matches what a workspace key can do; workspace:inference allows only Messages, token counting, Models and the OpenAI-compatible endpoint, which is enough for a job that just calls Claude.

What happens at run time

The identity token at the heart of this is an OpenID Connect ID token: a JSON Web Token, three base64url segments, signed by the issuer's private key. Its claims say who issued it (iss), whom it describes (sub), whom it is for (aud), and when it was issued and expires (iat, exp). Anyone can verify it by fetching the issuer's published public keys. Nobody can forge one without the issuer's private key.

The exchange follows three steps in Anthropic's documentation:

  1. The platform hands the workload a JWT. On GitHub Actions a job asks a runner-provided endpoint, which only works if the job has the id-token: write permission. On Google Cloud it comes from the metadata server; on Azure from the Instance Metadata Service; on AWS from STS's GetWebIdentityToken; on Kubernetes from a projected service-account token file.
  2. The SDK exchanges it. It posts the JWT to POST /v1/oauth/token on api.anthropic.com using the RFC 7523 jwt-bearer grant, along with the rule ID, organization ID, service account ID and, where needed, workspace ID. These IDs identify; they are not secrets. Anthropic verifies the signature against the issuer's keys (asymmetric algorithms only; HMAC and none are rejected), requires sub, iat and an unexpired exp, caps the JWT's own lifetime at an hour by default, and, by default, rejects a reused jti as a replay. Then it checks the rule. On success it returns an access token beginning sk-ant-oat01- and an expires_in.
  3. The SDK uses and refreshes it. Your code builds the client with no key. The SDK attaches the token as Authorization: Bearer, tries to refresh 120 seconds before expiry and must succeed by 30 seconds before.

A failed exchange returns the same opaque 401 "Authentication failed" whatever went wrong; the reason appears on the Console's authentication history tab. The docs don't say why; the effect is that someone probing your rules learns nothing from the reply.

The minted token's lifetime is the lesser of the rule's setting and twice the remaining life of the JWT you presented, and never under 60 seconds. That second bound matters for GitHub, whose tokens expire about five minutes after issue: an Anthropic token derived from one lasts at most about ten minutes, however generous the rule.

Not a new idea, just a new door

None of this was invented for Claude. The cloud providers have used the same pattern for years, in the other direction. GitHub's documentation describes the payoff: "You won't need to duplicate your cloud credentials as long-lived GitHub secrets." AWS accepts an OIDC token through STS AssumeRoleWithWebIdentity and returns temporary credentials for an IAM role whose trust policy names the issuer and conditions on its claims. Google Cloud's Workload Identity Federation trades external tokens through its Security Token Service, which implements RFC 8693 token exchange. Azure attaches "federated identity credentials" (issuer, subject and audience) to an app registration or managed identity.

Anthropic's version is the same shape with Anthropic as the party doing the checking. One technical difference: it uses the RFC 7523 JWT-bearer grant rather than RFC 8693 token exchange. Both are OAuth 2.0 extensions that let a signed assertion be swapped for an access token.

What federation can't do

The dialog's last line is the honest one: "Local scripts, third-party tools, and environments without an identity provider may still need an API key." Federation needs a party that can sign a token about your code and that Anthropic can reach to fetch public keys. Your MacBook has no such issuer, and neither does an app installed on someone else's Mac. Anthropic's own authentication guide recommends API keys for "local development, prototyping, scripts, and servers where you control secret storage."

Federation also moves trust rather than removing it. The token is "only as strong as the upstream identity provider that signs the JWT," and Anthropic warns that "a long-lived secret one step earlier in that chain," such as a static cloud credential able to mint tokens, can undermine it. On GitHub, anyone who can make a workflow run that matches your rule can obtain a token, which is why the docs warn that a loose rule such as repo:your-org/* also matches pull requests from forks.

Two other options appeared alongside it. ant auth login runs a browser OAuth flow for the ant CLI and stores credentials on disk; Anthropic says it is meant for "local development and scripting on your own machine." App Attest lets genuine installs of a registered iOS or macOS app get one-hour, Messages-only tokens billed to the developer's workspace, for apps with no back end. ELI5 Learner asks each user for their own key, so App Attest would mean paying for everyone's usage: a business decision, not a security fix.

What it means for ELI5 Learner

The Mac app keeps its API key. It runs on your Mac (and on users' Macs) with no identity provider, which is exactly the case the dialog carves out. The Keychain is the right home. Two small hygiene steps fit Anthropic's guidance: use a personal key (acts as you) rather than a legacy workspace key, and give it a name you'll recognize so you can delete it at once if it ever leaks. An expiration is optional; the trade-off is that the app stops working until you paste a new key.

The nightly evals are a good fit for federation. The evals job in .github/workflows/ci.yml runs only on schedule and workflow_dispatch, and today it reads the Claude key from the ANTHROPIC_API_KEY repository secret into ELI5_EVAL_API_KEY_CLAUDE. Anthropic documents GitHub Actions as a supported issuer, with a dedicated guide. The move would look like this:

  1. In the Console, run Connect workload › GitHub Actions. Create a service account such as eli5-nightly-evals in the workspace the evals bill to.
  2. Pin the rule tightly: subject_prefix repo:knail1/eli5-learner:ref:refs/heads/main (no *), audience https://api.anthropic.com, and claim repository_owner: knail1. Scheduled runs use the default branch, so their sub should have that form; confirm with the Console's test window or authentication history. Choose scope workspace:inference, since evals only call Messages.
  3. Give the evals job id-token: write. It has its own permissions block, which replaces the workflow-level one, so add it there.
  4. Change the eval runner's Claude path to build the SDK client with federated credentials instead of apiKey. Today the app's provider passes apiKey explicitly, and in the TypeScript SDK an apiKey or authToken, including one picked up from ANTHROPIC_API_KEY or ANTHROPIC_AUTH_TOKEN, takes precedence over credentials.
  5. Once a run succeeds, remove the secret from the workflow and from GitHub, then delete the key in the Console. The OpenAI key stays a secret; this changes only the Claude side.

Workflow change · adapted from Anthropic's GitHub Actions guide

  evals:
    if: github.event_name == 'schedule' || github.event_name == 'workflow_dispatch'
    runs-on: macos-latest
    permissions:
      contents: read
      issues: write
      id-token: write            # lets this job request a GitHub OIDC token
    env:
      # IDs from the Connect workload wizard. Identifiers, not secrets.
      ANTHROPIC_FEDERATION_RULE_ID: fdrl_...
      ANTHROPIC_ORGANIZATION_ID: 00000000-0000-0000-0000-000000000000
      ANTHROPIC_SERVICE_ACCOUNT_ID: svac_...
      ANTHROPIC_WORKSPACE_ID: wrkspc_...
      ELI5_EVAL_API_KEY_OPENAI: ${{ secrets.OPENAI_API_KEY }}
      # ELI5_EVAL_API_KEY_CLAUDE removed: no Claude secret in this job

One wrinkle needs care. GitHub's tokens last about five minutes, Anthropic by default treats each token's jti as single-use, and the minted token then lasts at most about ten minutes, while an eval run can easily take longer. Anthropic's guide shows writing the token to a file once, which works for short jobs. For a long one it suggests re-fetching periodically or giving the SDK a function that asks GitHub for a fresh token on each exchange. The installed SDK (0.128) exposes that hook:

Sketch, not tested · built from the SDK's documented types

import Anthropic from '@anthropic-ai/sdk';
import { oidcFederationProvider } from '@anthropic-ai/sdk/lib/credentials/oidc-federation';

// A fresh GitHub OIDC token for every exchange (they last ~5 min and are single-use).
async function githubIdToken(): Promise<string> {
  const url = `${process.env.ACTIONS_ID_TOKEN_REQUEST_URL}&audience=https://api.anthropic.com`;
  const res = await fetch(url, {
    headers: { Authorization: `Bearer ${process.env.ACTIONS_ID_TOKEN_REQUEST_TOKEN}` },
  });
  if (!res.ok) throw new Error(`GitHub OIDC request failed: ${res.status}`);
  return (await res.json()).value;
}

const client = new Anthropic({
  apiKey: null,     // null (not undefined) stops ANTHROPIC_API_KEY from winning
  authToken: null,  // same for ANTHROPIC_AUTH_TOKEN
  credentials: oidcFederationProvider({
    identityTokenProvider: githubIdToken,
    federationRuleId: process.env.ANTHROPIC_FEDERATION_RULE_ID!,
    organizationId: process.env.ANTHROPIC_ORGANIZATION_ID!,
    serviceAccountId: process.env.ANTHROPIC_SERVICE_ACCOUNT_ID,
    workspaceId: process.env.ANTHROPIC_WORKSPACE_ID,
    baseURL: 'https://api.anthropic.com',
    fetch,
  }),
});

Never print either token in logs. The GitHub request token and the minted sk-ant-oat01-… are both live credentials while they last.

The bottom line: click "Continue with an API key" for the Mac app; that is the case the dialog itself exempts. For CI, "Set up identity federation" is worth doing for the eval job: it removes the only long-lived Claude secret in the repo, and the worst a stolen token can do is last a few minutes in one workspace, at inference scope. Pin the rule to knail1/eli5-learner on main, never a wildcard, and remove the old secret only after a federated run succeeds.

Glossary

API key
A static sk-ant-api… bearer secret. Personal, service-account or (legacy) workspace type.
Bearer token
Any credential that works for whoever presents it, sent as Authorization: Bearer ….
Service account
A named non-human identity (svac_…) in your Anthropic organization. Has credentials; is not one.
Workload
Code running unattended somewhere: a CI job, a container, a cloud function.
Identity provider / issuer
The system that signs tokens about the workload, named by the iss claim. GitHub's is https://token.actions.githubusercontent.com.
OIDC ID token / JWT
A signed JSON Web Token carrying claims such as iss, sub, aud, exp.
JWKS
The issuer's published set of public keys, used to verify token signatures.
Federation issuer, rule
Console objects (fdis_…, fdrl_…): which issuer to trust, and which tokens from it may act as which service account, with what scope and lifetime.
jwt-bearer grant (RFC 7523)
The OAuth 2.0 method Anthropic's /v1/oauth/token uses to swap a signed JWT for an access token.
Token exchange (RFC 8693)
A related OAuth 2.0 standard, used by Google Cloud's STS; not what Anthropic's endpoint uses.
jti
A unique token ID. Anthropic accepts each one once per issuer, to block replays.
Scope
The ceiling on what a minted token may call, e.g. workspace:inference or workspace:developer.

ELI5

The short version: a key, or a pass from the front desk

Picture Claude as an office building with a front desk. To get in, you need something the desk accepts.

The old way is a door key. That's an API key. You get it once and it opens the door every time. The desk never asks your name, only whether the key fits. That is handy, and it is also the problem: if you drop the key in the street, whoever picks it up walks in as you, and keeps walking in until you notice and change the lock.

The new way, the one the dialog offered, is a visitor pass. You carry no key at all. Instead, someone the desk already trusts vouches for you each time, and the desk prints you a paper pass that stops working in a few minutes.

Who's who in the building

  • The robot is your code running somewhere by itself, like the nightly test job on GitHub.
  • The badge is a signed note from the robot's employer, GitHub, saying "this is a job from the eli5-learner project, on the main branch, running right now." Nobody can fake GitHub's signature, and the desk can check it against GitHub's public stamp.
  • The robot's name tag is a service account. It's not a key. It's a name, like "nightly-evals robot," so the building's logbook says which robot came in, not just "someone with a key."
  • The list at the front desk is something you write once in the Claude Console: "Badges signed by GitHub, for the eli5-learner project, on the main branch, may get a pass with the nightly-evals robot's name on it." That's the issuer plus the rule.
  • The pass is the short-lived token. It lets the robot talk to Claude for a few minutes. The robot's helper (the SDK) quietly asks for a new pass before the old one runs out.

The win: there is no key to lose. If someone steals a pass, it is useless in minutes. If someone copies your project's code, they still can't get a GitHub badge that says "main branch of your project."

Why your Mac app still needs a key

Passes only work when someone the desk trusts is there to sign a badge. GitHub can do that for its robots. Big cloud companies can do it for theirs.

Your Mac can't. When ELI5 Learner runs on your laptop, there is no employer standing behind it to vouch. That's what the small print in the dialog means: "Local scripts, third-party tools, and environments without an identity provider may still need an API key."

So the Mac app keeps its key, and the key lives in the macOS Keychain, a locked drawer that only your logged-in Mac can open. That is the right place for it. The rule is the same as for any house key: don't make copies, don't leave it lying in files, and if you ever think it's been lost, cancel it in the Console and make a new one.

What you'd actually do

Mac app: pick "Continue with an API key." Nothing changes.

Nightly evals on GitHub: this is where passes shine. Today the test job carries a copy of your door key, stored as a GitHub secret. Instead you could:

  1. Make a robot name tag (service account) called something like eli5-nightly-evals.
  2. Write the front-desk list: GitHub badges, only your eli5-learner project, only the main branch. Never "any project of mine," which would also let strangers' pull requests in.
  3. Let the test job ask GitHub for badges (id-token: write) and change the eval code to ask for passes instead of using a key.
  4. After one good night's run, throw away the old key and the GitHub secret.

One trap: if a key is still lying around, the helper uses the key and never asks for a pass. Remove ANTHROPIC_API_KEY from the job, or the switch silently doesn't happen.

That's the whole idea. A key is something you have to keep safe forever. A pass is something nobody has to keep safe at all, because by the time anyone could misuse it, it has already expired.
