Signing your Android app, explained

Google Cloud asked you for two SHA-1 fingerprints to set up Google sign-in. This page explains what those strings are, why they are safe to publish, and why the key behind the release one must never be lost or leaked.

In depth

The 40-Character Name Google Uses for Your App

Why a Google Cloud form asked for a string like CF:43:8F:…:22:DC, what it proves, and what it costs to lose the key behind it.

The Google Cloud form for an "Android" OAuth client asks for two things and nothing else: a package name and a "SHA-1 signing certificate fingerprint." It wants no client secret, no redirect URL and no app-store link. For ELI5 Learner the package name is io.github.eli5learner, and the fingerprint is the 59-character string CF:43:8F:EA:DF:22:55:97:16:2E:09:53:90:D1:CA:A8:11:9C:22:DC, which is 40 hex digits with colons between each pair.

That string identifies the app to Google. It is a hash of the certificate that signed the APK now sitting in release/android/, and the certificate in turn is backed by a 4,096-bit RSA private key stored in ~/.config/eli5-learner/eli5-release.jks. When someone taps "Sign in" on a phone, Google never sees a password or a client ID from ELI5 Learner, because the app embeds neither. Google Play services on the device reports which package is asking and which certificate signed it, and Google looks for a registered client that matches both.

Why it matters: app signing is not a formality that ends at build time. The same key decides whether Android will install your next update over the current one, whether Google sign-in works, and whether you can register the package under Android's developer-verification rules. The fingerprint is safe to publish: nobody can sign as you without the private key. Its one practical exposure is that a package-plus-SHA-1 pair can be claimed by only one Google Cloud or Firebase project, so register your Android clients promptly. The key behind it has to stay secret, and if it is lost it cannot be recovered.

A signature with no authority behind it

Every Android app must be signed by its developer before it can be installed. Unlike the certificates that secure websites, Android signing certificates are self-signed: developers "can generate without external assistance or permission," in the words of Android's security documentation, and no certificate authority vouches for them. Running keytool -genkeypair on your own Mac creates one.

That sounds weak until you see what the signature is for. It does not prove that you are a real company; anyone could make a certificate that also says CN=ELI5 Learner. It proves integrity and continuity: the APK has not been altered since it was signed, and whoever signed version 2 holds the same private key as whoever signed version 1. When Android installs an update, the system "compares the certificate(s) in the new version with those in the existing version. The system allows the update if the certificates match." The same rule underpins signature-level permissions and the old shared-user-ID mechanism, which both trust only apps signed with the same certificate.

How the signature sits inside the file has changed over time. The original scheme (v1, JAR signing, from Android 1.0) signed individual ZIP entries and left the ZIP metadata unprotected. That gap was exploited by the 2017 "Janus" vulnerability (CVE-2017-13156), which affected Android 5.0 through 8.0 (patched in the December 2017 security bulletin) and only APKs verified with a v1 signature alone; v2 signatures on Android 7.0 and later were not affected. APK Signature Scheme v2, introduced in Android 7.0, signs the whole archive. An APK Signing Block placed just before the ZIP central directory covers the entry contents, the central directory and the end-of-directory record, hashed in 1 MB chunks so the check runs in parallel and installs go faster. v3 (Android 9) adds key rotation, v3.1 (Android 13) targets rotation at newer platforms, and v4 (Android 11) supports streaming installs through a separate .idsig file.

ELI5 Learner's release APK carries only a v2 signature. Running apksigner verify -v --print-certs on it reports "Verifies," with v2 true and v1, v3 and v4 false. That is correct for this app: minSdk is 31, and v1 only matters for devices older than Android 7.0. Apps that target API 30 or higher must be signed with "APK Signature Scheme v2 or higher" to install on Android 11 and later, so a v2-or-newer signature is required; v2 is what this build uses.

What a fingerprint is, and why SHA-1

Android's documentation calls a certificate fingerprint "a short and unique representation of a certificate that is often requested by API providers alongside the package name to register an app." Technically, it is a hash of the certificate's DER-encoded bytes. On this Mac, exporting the debug certificate and piping it through shasum -a 1 gives exactly the SHA-1 that keytool prints. One certificate has one MD5, one SHA-1 (20 bytes) and one SHA-256 (32 bytes) fingerprint. None of them is a key.

Choosing SHA-1 can look odd in 2026. NIST disallowed SHA-1 for generating digital signatures after 2013 and plans to retire it entirely by 31 December 2030. What attackers broke, though, was collision resistance: the 2017 SHAttered attack produced two inputs with the same hash. To impersonate ELI5 Learner, an attacker would need a certificate that hashes to an existing, registered value. That is a second-preimage attack, and none is known to be practical for SHA-1. The APK signature itself is checked with RSA-4096 over SHA-256 digests (scheme v2); SHA-1 appears only in the fingerprint Google uses as a lookup label. Google has not published its reasoning, so treat this as an informed reading rather than official policy. Whatever the reason, the form wants SHA-1, so paste the line labelled SHA1, not SHA-256 or MD5.

"…it's intended to be shared, as it does not contain your private key."

The fingerprint is a hash of exactly that shareable certificate, so the same reasoning covers it.

What happens when you tap "Sign in"

ELI5 Learner syncs through the Drive appDataFolder using three scopes: openid, userinfo.email and drive.appdata. On Android it uses Google's AuthorizationClient, which Google recommends for accessing account data such as Drive, as opposed to Credential Manager, which handles plain authentication. The sequence:

  1. The app builds a request. AuthorizationRequest.Builder.setRequestedScopes() takes the scope list and nothing else. No client ID is involved; one would only be needed for requestOfflineAccess(serverClientId), which serves a backend server.
  2. Play services identifies the caller. Android knows the requesting app's package and the certificate it was verified against at install time. Play services passes io.github.eli5learner and that certificate's identity to Google.
  3. Google looks for a match. It searches for an Android OAuth client registered with that exact package and SHA-1. Each pair may exist in only one Google Cloud or Firebase project (Firebase support). Because both values are public, a third party could in principle register the pair first; they still could not get tokens without your private key, but you would be blocked from registering it. If Google ever reports "already exists in another project," raise it with Google support; signing with a new key is the only workaround.
  4. The user consents. If the result hasResolution(), the app launches the returned PendingIntent and the consent screen appears, branded with the project's consent-screen settings.
  5. A token comes back. The result carries an access token valid for about an hour. Later calls to authorize() return a fresh token without prompting while the grant stands. Google advises against storing refresh tokens on the device.
  6. The app learns who signed in. Authorization responses don't name the account, so the app calls the userinfo endpoint with the token. That is why openid and userinfo.email are in the scope list.

The Mac app follows a different path. It uses a "Desktop app" client, which takes no fingerprint, and a loopback redirect to 127.0.0.1 on a random port, protected by PKCE. Google has deprecated loopback redirects for Android clients, so each platform uses its own client type.

Testing mode caveat. While the consent screen's user type is External and its publishing status is "Testing," you can list at most 100 test users, and refresh tokens Google issues expire after 7 days because drive.appdata is outside the openid/email/profile exemption (Google OAuth 2.0, token expiration). Expect the Mac app to need re-consent about weekly. Google doesn't document how this affects Android's AuthorizationClient, which holds no refresh token, so test it. Moving to Production removes the limit; check the current verification requirements for your scopes in the console when you do.

The Android client's optional "Verify app ownership" step works only for apps registered in Play Console. Leave it unverified for a sideloaded build; sign-in still works.

Two keys, two clients

ELI5 Learner is signed by two different keys depending on how it is built. A debug build from Android Studio or ./gradlew assembleDebug is signed automatically with ~/.android/debug.keystore, which the build tools created on this Mac. It holds alias androiddebugkey, password android, an RSA 2048 key and a certificate valid until 2056, with SHA-1 54:C1:10:…:A0:2D. A release build is signed with the eli5 key, SHA-1 CF:43:8F:…:22:DC.

An Android OAuth client holds one package and one SHA-1, so ELI5 Learner needs two clients, both for io.github.eli5learner. Register only one and sign-in fails for the other build. Google's client-auth guide tells you to collect both the release and debug fingerprints; because each Android client takes one SHA-1, that means one client per key.

Three practical consequences follow:

  • The debug key belongs to this Mac. A new laptop, a CI runner or a deleted ~/.android produces a new debug key with a new SHA-1, and the debug client stops matching. Copying the keystore file between machines keeps the SHA-1 stable.
  • The release build can silently use the debug key. Stock Gradle would produce an unsigned release APK, but this project's android/app/build.gradle.kts deliberately falls back to the debug signing config when the ELI5_ANDROID_* properties are missing. A file named eli5-learner-release.apk built on another machine may therefore carry the debug SHA-1. Check the actual APK with apksigner verify -v --print-certs and read the certificate SHA-1 digest line, not the "public key SHA-1 digest" line next to it. apksigner prints the fingerprint as lowercase hex without colons (cf438fea…22dc); it is the same value as CF:43:8F:…. keytool -printcert -jarfile <apk> prints the colon form if you want an exact visual match.
  • You can't switch an installed copy between debug and release. Installing one over the other fails with INSTALL_FAILED_UPDATE_INCOMPATIBLE, shown on the phone as "App not installed." Neither adb install -r nor -d gets around it. The fix is adb uninstall io.github.eli5learner, which deletes local app data. To keep both builds installed side by side, add an applicationIdSuffix such as .debug. That changes the package name, so the debug OAuth client must then use the suffixed package.

Play App Signing versus sideloading

Much Google documentation assumes Play App Signing. In that model you sign uploads with an upload key, and Google re-signs what users install with an app signing key that only Google holds. The certificate on users' phones is then Google's, so Google warns that "you must register the Google-held app signing key fingerprint with your API providers, not just your local upload key."

None of that applies to ELI5 Learner today. Nothing re-signs a sideloaded APK, so the certificate Google OAuth sees is the one from eli5-release.jks. If the app ever moves to Play with a Google-generated signing key, it would need a third Android client for the SHA-1 shown on Play Console's app signing page. Uploading your own release key when you enroll in Play App Signing avoids that. It means handing Google a copy of the private key (through the encrypted export the Play Console provides); you keep your own copy and backups as before.

Sideloading is also changing. Under Android developer verification, apps on certified devices must be registered to a verified developer, with the package name tied to its signing key. Enforcement began on 30 September 2026 in a few countries, and Google plans to expand it globally in 2027; its FAQ indicates that sideloaded installs are not yet affected during the first phase. Google's FAQ also says "Apps installed using ADB won't require verification," so adb install -r keeps working. Once enforcement covers sideloading, tapping an APK of an unregistered app in Files or Drive will need the device's one-time "advanced flow" (developer mode, a restart, a 24-hour wait, then biometric confirmation, after which installs are allowed for 7 days or indefinitely); updates to unregistered apps need the same, or ADB. A free limited-distribution account can register the package instead, but it is limited to 20 specific devices, for testing and personal use; wider distribution needs a full-distribution account ($25, with ID verification). Registration is proven with the signing key. Google changed this policy several times in 2025 and 2026, so re-check the FAQ before the global rollout.

If the key is lost, or leaked

Google is blunt about this: "You cannot regenerate a previously generated key." Without Play App Signing, nobody can recover it. For ELI5 Learner, losing the .jks file or its passwords would mean every installed copy must be uninstalled, losing its local data, before a build signed with a new key can go on. The release OAuth client would need a new SHA-1, and if the package is registered for developer verification, you would have to register the new key (or a new package) as well.

Key rotation under v3 does not help. apksigner rotate requires the old signer's keystore, so it is a way to migrate away from a key you still have, not a way to replace one you lost. By default apksigner applies a rotated key only on Android 13 and later (the v3.1 block), because rotation had known bugs on Android 11 and 12; older devices keep checking the original key. With minSdk 31, devices on Android 12 and 12L would keep needing the old key.

Leaking the key is as bad as losing it, or worse. Anyone with the file and its passwords can build an "update" that phones will accept over your app, with access to its data. If that happens, stop using the key and move to a new package and a new key.

Key point: the signing identity is the file eli5-release.jks plus the keystore and key passwords in ~/.gradle/gradle.properties (ELI5_ANDROID_KEYSTORE_PASSWORD and ELI5_ANDROID_KEY_PASSWORD; they may be identical, but back up both). A backup of the file without the passwords is useless. Store the keystore in an encrypted backup and the passwords in a password manager, both somewhere other than this Mac, and never in the public repo. The key's validity of 10,000 days, about 27.4 years, meets Google's 25-year recommendation, so expiry is not a concern before March 2054.

Troubleshooting "Developer error (10)"

When Play services finds no match, it usually returns CommonStatusCodes.DEVELOPER_ERROR (10): "The application is misconfigured. This error is not recoverable and will be treated as fatal. The developer should look at the logs after this to determine more actionable information." The most common cause is that no registered client matches the installed APK's package and SHA-1, but an incomplete consent screen or the wrong project can trigger it too. Check in this order:

  1. What do the logs say? Run adb logcat and reproduce the failure; look for the Play services or auth message logged at that moment.
  2. Which key signed the installed APK? Run apksigner verify -v --print-certs on that exact file, or ./gradlew signingReport for Gradle variants.
  3. Is that SHA-1 registered? Confirm there is an Android client with exactly that fingerprint. SHA-256 or MD5 pasted by mistake will not match.
  4. Does the package match the applicationId? A suffix or a product flavor changes it.
  5. Is everything in one project? Keep the Android clients, the Desktop client, the consent screen and the enabled Google Drive API in the same Google Cloud project.
  6. Was the client just created? Google says changes can take "5 minutes to a few hours" to apply.
  7. Is the client still there? Clients are deleted after six months of inactivity, with an email 30 days beforehand; deleted clients are typically restorable for at least 30 days. Restore a deleted client inside that window rather than recreating it.

Other setup problems surface differently: a Google account that is not on the test-user list gets access_denied, for example. Because error 10 is fatal, the app should show a clear "sign-in is misconfigured" message instead of retrying. NETWORK_ERROR (7) is the one worth retrying.

Glossary

Keystore
A file (.jks, .keystore, PKCS12) holding private keys and certificates under aliases. Secret.
Alias
The name of one key in a keystore: eli5 for release, androiddebugkey for debug.
Certificate
The public key plus owner details, self-signed on Android. Ships inside the APK.
Fingerprint
A hash (MD5, SHA-1 or SHA-256) of the certificate bytes. Public; used to register the app with API providers.
APK Signature Scheme v2
Whole-file signing introduced in Android 7.0. ELI5 Learner's release APK uses it.
Android OAuth client
A Google Cloud registration of one package plus one SHA-1. Has no client secret.
Desktop app client
The Mac app's OAuth client, using a loopback redirect and PKCE. Takes no fingerprint.
Play App Signing
Google re-signs apps distributed through Play with a key it holds. Not used for sideloaded builds.
INSTALL_FAILED_UPDATE_INCOMPATIBLE
The install error when an installed package has a different signature from the new one.
DEVELOPER_ERROR (10)
Play services' fatal "misconfigured" status, usually a package or SHA-1 mismatch.

ELI5

The short version: your app has a wax seal

Picture an old-fashioned letter closed with a wax seal. The sender presses a signet ring into hot wax. Anyone who sees an unbroken seal can tell the letter wasn't opened, and that it came from the same ring as the last letter. It doesn't prove who you are, only that it's the same you each time.

Android apps work the same way. Every APK is sealed before a phone will install it. Your ELI5 Learner APK, package io.github.eli5learner, carries a seal pressed by your own ring. You made the ring yourself. No authority is needed to make the ring.

Separately, Google is starting to require that apps on certified phones are registered to a verified developer: in a few countries from September 2026, and worldwide in 2027. Installs over USB with adb are exempt. If you hand the APK to other people after that, register io.github.eli5learner and this key in the Android Developer Console (a free account type covers up to 20 devices for testing and personal use).

The pieces, in seal language

  • The ring is the private key. It lives in a locked box (the keystore file) that opens with a password. It is the only secret part.
  • The seal is the signature pressed onto this exact APK, together with a card (the certificate) showing your ring's pattern. Anyone can read the card. Only your ring can make a seal that matches it, and changing even one byte of the APK breaks the seal.
  • The fingerprint (SHA-1) is a short description of the pattern on the card, something like "eagle facing left, three stars". It is 20 bytes, written as 40 hex digits, usually in pairs separated by colons, calculated from the certificate. It helps nobody forge the ring, so it is safe to publish.

Fingerprints and the package name are public. The keystore file and its password(s), meaning the store and key password entries in ~/.gradle/gradle.properties, are secret. Treat the practice ring's file (below) as private too.

Why the phone cares: updates

When you install a new version, the phone checks the seal, then compares the card with the one on the copy already installed. If they match, the update goes through and your data stays. If they don't, the phone refuses with a message like "App not installed". To the phone, a different card means a stranger is trying to replace your app.

You have two rings, and they make different seals:

  • A practice ring (debug key). The build tools made it automatically at ~/.android/debug.keystore. Its password is the well-known "android", but the ring itself is unique to this Mac, so don't share the file. It is used for builds you run from your Mac while developing. Each Mac makes its own practice ring.
  • The real ring (release key). You made it on purpose: ~/.config/eli5-learner/eli5-release.jks, alias eli5. It signs the APK in release/android/.

Since the two seals differ, a debug build can't be installed over the release build (or the other way round). You have to uninstall first, and that deletes the app's data on the phone.

Google sign-in: the bouncer with a guest list

When the app asks for Google Drive access, Google's helper on the phone (Play services) acts like a bouncer. It doesn't ask for a password. It looks at two things: the app's name (the package) and its card. It then checks a guest list you keep in Google Cloud.

Each entry on the guest list is an "Android" OAuth client, and each one holds exactly one name and one fingerprint. That is why Google asked you for SHA-1 fingerprints. It is also why your app embeds no client ID: the seal itself identifies the app.

Your Mac app goes through a different door. It uses a "Desktop app" client that signs in through the browser, and it has no seal involved at all.

What you actually have to do

  1. In the Google Cloud project, enable the Google Drive API, set up the consent screen (Branding), and add your own Google account as a test user.
  2. Create an Android OAuth client with package io.github.eli5learner and SHA-1 54:C1:10:61:F7:33:98:E7:99:C1:2E:AA:61:1B:71:DE:2B:D9:A0:2D (debug).
  3. Create a second Android client with the same package and SHA-1 CF:43:8F:EA:DF:22:55:97:16:2E:09:53:90:D1:CA:A8:11:9C:22:DC (release). Do both soon: each name-plus-fingerprint pair can be claimed by only one project.
  4. Paste the line labelled SHA1, not SHA-256 or MD5. If you read it from apksigner, use "certificate SHA-1 digest", not "public key SHA-1 digest". apksigner shows it as cf438fea… (lowercase, no colons); it's the same value as CF:43:8F:EA:…, and keytool shows the colon form.
  5. Keep the Mac's "Desktop app" client separate, in the same project. It doesn't need a SHA-1.
  6. If sign-in fails right after setup, wait. Changes can take minutes or a few hours to reach every server.
  7. While the app stays in Testing, the Mac app's sign-in expires after 7 days and will ask again. Test whether Android does the same. Publishing to Production removes that limit.
  8. Not sure which seal an APK carries? Run apksigner verify -v --print-certs on that exact file.

Things that quietly change a seal: a new Mac or a deleted ~/.android folder makes a new practice ring, so the debug entry stops matching. In this project's build script, a release build made without your four ELI5_ANDROID_* signing settings silently falls back to the practice ring, and the file is still called a release APK. Before sharing any APK, check that its SHA-1 is CF:43:…:22:DC. If you ever add a suffix such as .debug to the debug build's name, the debug guest-list entry has to use that name too.

If you ever publish on Google Play with Play App Signing, Play re-signs the app with a different key. Add another Android client with the SHA-1 from Play Console's App signing page.

The one thing never to lose

The real ring and its passwords: ~/.config/eli5-learner/eli5-release.jks, plus the keystore password and key password (ELI5_ANDROID_KEYSTORE_PASSWORD and ELI5_ANDROID_KEY_PASSWORD, which currently live only in ~/.gradle/gradle.properties; they may be identical). Back up both.

A ring can't be recreated. If you lose it, or lose the passwords, no update will ever install over existing copies. Everyone would have to uninstall, lose their local data and start again, you would need a new guest-list entry, and if you have registered the app for developer verification you would have to register the new key as well. A backup of the ring without its passwords is useless.

Leaking it is just as bad: anyone with the file and passwords can make an "update" your phone will accept. If that happens, stop using the key and move to a new package and a new key.

So back up both, separately and away from this Mac: for example, the file in an encrypted backup and the passwords in a password manager. Never put either in the public repo. The fingerprints can go anywhere.

The ring is good for 10,000 days, until March 2054, so expiry isn't something to worry about. Losing it, or leaking it, is.
